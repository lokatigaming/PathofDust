src/adventure/combat.rs:simulate_battle (boss_pierce_pct) — new mechanic, not a bugfix: a stage-scaled fraction of every REAL boss's attack (named world bosses only — never basic encounters, never player attacks, never a boss's own DoT/true-damage abilities like Doom or Hemorrhage explosions) now resolves as unavoidable, unmitigable true damage before the rest of the hit runs the normal evasion/block/damage-reduction/crit pipeline as usual. Formula: boss_pierce_pct = PIERCE_CAP_PCT * stage^2 / (stage^2 + PIERCE_H^2) — a quadratic-then-asymptotic ramp that reaches half of PIERCE_CAP_PCT at stage PIERCE_H and climbs toward, but never reaches, PIERCE_CAP_PCT itself. At live stage ~821 this is ≈7% pierce; ~18% at stage 1500; ~35% at stage 3000. Both PIERCE_CAP_PCT (default 0.5 → 50%) and PIERCE_H (default 2000) are LiveTunables (adventure-live-tunables.toml, admin-editable at /admin/tunables, re-read every fight) — NOT compile-time constants, so the wiki's placeholder substitution can't read them the usual `crate::adventure::CONST` way; wiring these two placeholders needs a live-value read path instead (e.g. through AdventureManager::live_tunables()), flagging this explicitly since every other wired placeholder to date has been a compile-time constant. Shields still absorb the pierce portion and death-prevention passives (Guardian Spirit, Undying Fury, Verdant Burst, Soul Stone, Chakra of Life) still trigger on it normally — only evasion/block/damage-reduction/intervene are bypassed. Directly increases effective incoming boss damage for every build, scaling up with stage — healers and shield-granting passives are more valuable now than before this landed — affects combat
src/adventure/combat.rs:resolve_hit (boss pierce split-point bugfix, same day as the above) — the formula/percentages above are unchanged, but the initial implementation carved the pierce fraction off the boss's raw pre-roll base damage instead of the fully-rolled hit, so pierce silently ignored boss_power_mult/increased-damage/crit almost entirely at live stage scaling (the pierce chunk was a rounding error, the normal mitigable pipeline was still carrying nearly all the real damage — the mechanic was live but had negligible real effect). Fixed same-day, before any real fight data was captured against it: pierce now splits AFTER the attacker-side roll (crit, increased damage, boss_power_mult — baked into the boss's base attack stat — and the late-stage penalty), so a boss with real crit/increased-damage investment now has its pierce chunk scale with that too. Invariant: against a target with zero evasion/block/DR, total damage taken is byte-identical whether pierce is on or off — pierce only ever redistributes WHERE damage is unavoidable, never how large the rolled hit is. No formula/percentage change, no wiki text change needed — affects combat
game/src/adventure/published_constants.rs (new) + wiki.rs:wiki_placeholder_map — architecture refactor: BUILTIN_COOLDOWN_S/BUGREPORT_COOLDOWN_S/VOTESKIP_COOLDOWN_S/MIN_VOTE_VOLUME/MAX_VOTE_VOLUME's data source changed. These 5 placeholders used to read the bot's own constants directly at render time; wiki.rs now lives in the `game` crate (owner's ruling: the standalone game must serve its full web UI, wiki included, with no bot process running), so it can no longer reach bot-side code directly. The bot now writes its own values for these 5 (all compile-time-fixed on the bot side, never live-changing) to a small shared file (`bot-published-constants.json`) once at every startup; wiki.rs reads that file per-request. Same real numbers in the normal case (bot has started at least once since deploy). New fallback state, previously impossible: if that file is missing or unparseable (bot never started, or a standalone `game` instance with no bot at all), all 5 placeholders render the literal word "varies" instead of a number. Confirmed live via a real standalone smoke test (game binary alone, no bot, /wiki/commands page): renders correctly, no crash — but the surrounding markdown text wasn't written expecting a word there, so it currently reads awkwardly ("Shared variess" from a template appending a literal "s" after the value; "!vv <varies-varies>" for the vote-volume range) — cosmetic only, worth a wording pass in wiki/commands.md whenever convenient (that file is owner/wiki-session-edited only, not touched here) — affects commands|wiki infrastructure
